# Maal Help — Database

PostgreSQL 15+ in production. Local development and tests use **PGlite**, the same PostgreSQL engine compiled to WebAssembly, so constraints, triggers and SQL behave identically. The schema is defined in TypeScript with Drizzle ORM (`server/src/db/schema/*.ts`, snake_case columns). Migrations are in `server/drizzle/`.

## Migrations

| File | Contents |
|---|---|
| `0000_foundation.sql` | Generated by drizzle-kit: all 83 tables, foreign keys, unique constraints and indexes |
| `0001_ledger_immutability.sql` | Hand-written: append-only triggers on `inventory_transactions` and `audit_logs`, `CHECK (quantity >= 0)` on balances, search indexes |

```bash
npm run db:generate
```
creates a new migration after a schema change. `npm run db:migrate` applies pending migrations (the server also applies them on start).

> When regenerating, check that `0001_ledger_immutability.sql` is still intact: drizzle-kit does not know about custom SQL files.

## Integrity rules

| Rule | Mechanism |
|---|---|
| Stock history cannot be edited or deleted | Trigger `inventory_transactions_immutable` raises on UPDATE/DELETE |
| Audit history cannot be edited or deleted | Trigger `audit_logs_immutable` |
| No negative stock | `CHECK (quantity >= 0)` on `inventory_balances`, plus row locks in `postMovement` |
| One balance row per stock identity | `UNIQUE NULLS NOT DISTINCT (tenant, warehouse, location, product, batch, owner, status)` |
| Tenant isolation | `tenant_id` on every business table, with `ON DELETE CASCADE` from tenants; scoped in every query |
| Unique business numbers | `number_sequences` per tenant and document type (PO-, GRN-, SO-, INV-, TR-…) |
| Money and quantity precision | `numeric(18,4)` for quantity, `numeric(18,2)` for money, mapped to JS numbers |

> The trigger function is named `stockpilot_block_mutation`. This is a technical identifier from before the rebrand. Renaming it would need a migration and has no user-visible effect, so it was kept.

## Key columns

**inventory_transactions**: `transaction_type` (receipt, putaway, transfer_out/in, pick, dispatch, return, adjustment, count_adjustment, status_change, relocation, release…), signed `quantity`, `unit_cost`, `balance_after`, `reference_type/id/no`, `correlation_id` (groups the two sides of a move), `reason`, `performed_by`, `created_at`.

**inventory_balances**: identity columns plus `status`, `quantity`, `version`.

**products**: SKU, name, category, unit, barcodes (`product_barcodes`), dimensions (`volume_m3`, weight), tracking flags (batch / expiry / serial), reorder level and quantity, lead time, cost (moving average, updated on receipt) and sale price, tax rate.

## Demo data

`npm run db:reset` deletes the local PGlite directory (`PGLITE_DIR`, default `./.data/pg`), runs migrations and builds the fictional company **ABC Trading & Warehousing** by calling the real API for 120 simulated days. With `DATABASE_URL` set it drops and recreates the `public` schema instead, so **never** point it at a production database. It refuses to run when `NODE_ENV=production`.

Latest reset in this workspace: 3 warehouses, 94 products, 247 sales orders, 39 purchase orders, 3,156 ledger transactions.

## Backups

- Production PostgreSQL: use the provider's point-in-time recovery, plus a daily `pg_dump` to separate storage.
- Embedded PGlite (dev only): stop the server with Ctrl+C before copying `.data/pg`. A hard kill (for example Task Manager or `Stop-Process -Force`) can leave the embedded database unreadable. Recover with `npm run db:reset`.
